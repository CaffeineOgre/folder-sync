# Story 1.1 — Product Requirements & Scope Boundaries

**Epic**: 1 — Product Definition & Scope Management
**Milestone**: M1 — Architecture & Technical Specification Sign-off
**Status**: Draft for review
**Covers**: Task 1.1.1 (MVP vs. post-1.0 functional requirements), Task 1.1.2 (out-of-scope boundaries), Task 1.1.3 (hardware resource consumption bounds)

This document is a planning artifact. It defines *what* the product must do and the bounds it must operate within. It deliberately specifies no code, API contracts, database schemas, wire formats, or cryptographic primitives — those are the output of Epic 2.

---

## 1. Product Definition

### 1.1 Problem Statement

Users who want their files backed up and synchronized across machines currently must trust their cloud provider with plaintext content and — even where content encryption exists — with metadata: filenames, folder structure, file sizes, and modification times. That metadata is frequently sufficient to reconstruct sensitive facts about the user.

### 1.2 Product Statement

A single, self-contained Go binary that keeps one local directory synchronized with a user-owned cloud storage account, where the cloud provider observes only opaque encrypted objects. The user's password never leaves the machine, and neither does anything derived from it that would allow the provider to recover content or structure.

### 1.3 Primary Personas

| Persona | Description | Primary need |
| :--- | :--- | :--- |
| **P1 — Privacy-conscious individual** | Technical user syncing personal documents across 2–3 personal machines | Zero-knowledge guarantee; simple setup; no ongoing cost beyond their existing Drive quota |
| **P2 — Headless operator** | Runs the tool on a server, NAS, or VPS with no desktop session | Non-interactive auth and operation; service/daemon integration; structured logs |
| **P3 — Small-team practitioner** | Individual within a small org, syncing a working folder from their own account | Reliable conflict handling; predictable deletion semantics; ability to audit what happened |

Multi-user shared-folder scenarios are explicitly out of scope for v1.0 (see §4).

### 1.4 Product Principles

These principles are the tie-breakers when requirements conflict. They are ordered; earlier principles win.

1. **Confidentiality is not negotiable.** No feature ships if it weakens the zero-knowledge property. A feature that would require the provider to see plaintext or structure is not descoped-and-deferred, it is rejected.
2. **Never silently lose data.** When the correct action is ambiguous, the system preserves both sides and surfaces the ambiguity. Refusing to act is always preferable to destroying a user's file.
3. **Interruption is the normal case.** Power loss, network loss, and process kill are expected operating conditions, not exceptional ones. Every state transition must be resumable or rollback-able.
4. **The user's machine is theirs.** The tool must be a well-behaved background citizen: bounded memory, yielding CPU, no surprise bandwidth saturation.
5. **Ship a narrow tool that works.** A correct one-directory CLI sync is the v1.0 goal. Breadth is post-1.0.

## 2. Requirement Conventions

* **Identifiers**: `FR-<area>-<n>` for functional requirements, `NFR-<area>-<n>` for non-functional. Identifiers are permanent — a requirement that is removed is marked *Withdrawn*, never reused.
* **Priority**:
  * **M (Must)** — v1.0 GA does not ship without it.
  * **S (Should)** — targeted for v1.0; may be deferred at the M6 gate with explicit sign-off.
  * **D (Deferred)** — explicitly post-1.0; recorded here to bound v1.0, not to promise a date.
* **RFC 2119 terms** (*must*, *should*, *may*) carry their conventional meaning.
* **Traceability**: every **M** requirement must be referenced by at least one Epic 4 implementation task and at least one Epic 5 verification task before the M1 sign-off gate closes. Requirements with no downstream task are treated as a planning defect.

## 3. Task 1.1.1 — Functional Requirements

### 3.1 MVP (v1.0 GA) Functional Requirements

#### 3.1.1 Setup & Configuration (`CFG`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-CFG-1 | M | The user can initialize a sync relationship between exactly one local directory and one remote storage location via an interactive first-run flow. |
| FR-CFG-2 | M | The user can supply their own cloud OAuth client credentials, so that no shared/embedded application identity is required to operate the tool. |
| FR-CFG-3 | M | Configuration is persisted in a human-readable file at a documented, platform-conventional location, and all settings are overridable by environment variable and by command-line flag. |
| FR-CFG-4 | M | The tool validates configuration on load and refuses to start with a specific, actionable error rather than starting in a partially-configured state. |
| FR-CFG-5 | M | The user can exclude paths from synchronization using a pattern file, with documented and deterministic matching semantics. |
| FR-CFG-6 | S | Configuration changes that do not alter the encryption or remote-identity settings can be applied without a full re-scan. |
| FR-CFG-7 | M | A single machine runs at most one instance per configured sync directory; a second invocation fails clearly rather than corrupting shared state. |

#### 3.1.2 Security & Key Management (`SEC`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-SEC-1 | M | All file content is encrypted on the local machine before any byte is transmitted. |
| FR-SEC-2 | M | All file metadata — names, directory structure, sizes, and timestamps — is protected such that the storage provider cannot recover it. Residual observable properties are enumerated and bounded in Story 1.2. |
| FR-SEC-3 | M | Encryption keys are derived from a user-supplied password on the local machine. Neither the password nor any key material is transmitted to the provider. |
| FR-SEC-4 | M | During setup the user is issued a recovery secret and is required to acknowledge that losing both the password and the recovery secret renders the data permanently unrecoverable. |
| FR-SEC-5 | M | The user can change their password without re-uploading or re-encrypting file content. |
| FR-SEC-6 | S | The user may opt in to storing the password in the OS-native credential store to permit unattended startup. Opting in is a deliberate act, never a default. |
| FR-SEC-7 | M | Every downloaded object is integrity-verified before it is written into the user's directory; a failed verification aborts the write and reports the affected object. |
| FR-SEC-8 | M | Secrets — passwords, keys, recovery material, OAuth tokens — never appear in logs, error messages, crash output, or telemetry at any log level. |

#### 3.1.3 Synchronization (`SYN`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-SYN-1 | M | Initial sync: an empty remote is populated from a populated local directory, and an empty local directory is populated from a populated remote. |
| FR-SYN-2 | M | Bidirectional delta sync: changes made on any participating device converge on all other devices. |
| FR-SYN-3 | M | Detected change types include create, modify, delete, and rename/move for both files and directories. |
| FR-SYN-4 | S | A rename or move that does not change content is propagated without re-uploading the content. |
| FR-SYN-5 | M | Changes to the local directory are detected automatically while the tool is running, without user action. |
| FR-SYN-6 | M | A periodic full reconciliation scan runs on a configurable interval as a correctness backstop for missed or dropped filesystem events. |
| FR-SYN-7 | M | Rapid successive changes to the same path are coalesced so that transient editor write patterns do not produce a burst of remote operations. |
| FR-SYN-8 | M | Concurrent divergent edits to the same path are detected as conflicts rather than resolved by overwrite. |
| FR-SYN-9 | M | Conflict resolution policy is user-configurable across at least: preserve-both (rename one side), prefer-local, prefer-remote, and prompt. Preserve-both is the default. |
| FR-SYN-10 | M | The user can list unresolved conflicts and resolve them explicitly. |
| FR-SYN-11 | M | An interrupted sync resumes without duplicating completed work and without leaving partial files in the user's directory. |
| FR-SYN-12 | M | Changes made while offline are queued durably and transmitted on reconnection. |
| FR-SYN-13 | M | Empty directories are preserved across devices. |
| FR-SYN-14 | S | Symbolic links are handled according to a documented, configurable policy (at minimum: skip, with a warning). |

#### 3.1.4 Deletion & Retention (`DEL`)

Detailed specification is Story 1.3; the requirements below bound what v1.0 must offer.

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-DEL-1 | M | The user can select a deletion policy governing what a local deletion does remotely: immediate remote delete, remote soft-delete/archive, or append-only (never delete remotely). |
| FR-DEL-2 | M | Remote soft-delete/archive is the default policy. |
| FR-DEL-3 | M | A sync operation that would delete more than a configurable threshold of objects in one pass is halted and requires explicit user confirmation before proceeding. |
| FR-DEL-4 | M | The chosen deletion policy and its consequences are stated during setup, not buried in configuration. |
| FR-DEL-5 | S | Soft-deleted remote objects can be listed and restored via the CLI within a configurable retention window. |

#### 3.1.5 Cloud Backend & Transport (`NET`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-NET-1 | M | Google Drive is supported as the storage backend, authenticated by OAuth 2.0 against the user's own account. |
| FR-NET-2 | M | Authorization works on a machine with a browser and, via a copy-paste or device-code fallback, on a headless machine. |
| FR-NET-3 | M | Access tokens are refreshed automatically; expiry does not require user intervention. Refresh failure produces an actionable re-authorization prompt rather than a silent stall. |
| FR-NET-4 | M | Provider rate limiting and transient server errors are handled with retry and exponential backoff with jitter; the tool does not amplify provider degradation. |
| FR-NET-5 | M | Large transfers are chunked and resumable across process restart and network interruption. |
| FR-NET-6 | M | The storage backend is accessed exclusively through an internal abstraction boundary, such that adding a second provider post-1.0 requires no change to the sync engine or crypto layer. |
| FR-NET-7 | M | Loss of network connectivity degrades the tool to offline queuing; it does not crash, spin, or corrupt state. |

#### 3.1.6 Command-Line Interface & Operations (`CLI`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-CLI-1 | M | The CLI provides, at minimum: initialize, run/sync, status, pause, resume, conflict management, and configuration inspection. |
| FR-CLI-2 | M | A one-shot mode performs a single reconciliation pass and exits with a meaningful exit code, suitable for cron and CI use. |
| FR-CLI-3 | M | A long-running daemon mode operates continuously with no attached terminal and no interactive prompts. |
| FR-CLI-4 | M | Interactive runs display transfer progress, throughput, and remaining work. |
| FR-CLI-5 | M | A dry-run mode reports the actions that would be taken without mutating local or remote state. |
| FR-CLI-6 | M | Logging supports both human-readable and structured machine-readable output, with configurable level and rotation. |
| FR-CLI-7 | M | Exit codes distinguish success, configuration error, authentication error, network failure, and unresolved conflicts. |
| FR-CLI-8 | S | Installation as a managed system service is documented and scriptable for systemd, launchd, and Windows Services. |
| FR-CLI-9 | M | Every command supports `--help` with usage, flags, and at least one example. |

#### 3.1.7 Platform Support (`PLT`)

| ID | Priority | Requirement |
| :--- | :--- | :--- |
| FR-PLT-1 | M | Linux, macOS, and Windows are supported on x86-64 and ARM64, at feature parity, from a single codebase. |
| FR-PLT-2 | M | Filenames differing only in Unicode normalization form or in case are handled without sync loops, duplicate objects, or data loss across mixed-platform device sets. |
| FR-PLT-3 | M | Paths or filenames that are legal on the source platform but illegal on a destination platform are detected, skipped safely, and reported — never silently mangled. |
| FR-PLT-4 | S | POSIX permission bits are preserved between POSIX devices. Cross-platform attribute mapping follows a documented, lossy-but-predictable policy. |
| FR-PLT-5 | M | Distribution is a single self-contained binary per platform/architecture with no runtime dependency on a language runtime or interpreter. |

## 4. Task 1.1.2 — Out-of-Scope Boundaries

### 4.1 Permanently Out of Scope

These are excluded from the product as designed. Reversing one is a product redefinition, not a backlog addition.

| ID | Excluded | Rationale |
| :--- | :--- | :--- |
| OOS-P-1 | **Server-side processing of user data** — thumbnailing, indexing, search, virus scanning, preview generation, transcoding | Requires plaintext at the provider. Directly contradicts Principle 1. |
| OOS-P-2 | **Provider-native web/mobile UI access to synced files** | Files in the provider's UI are opaque ciphertext by design. Any usable in-provider view would require giving the provider keys. |
| OOS-P-3 | **Password recovery, key escrow, or vendor-assisted account recovery** | Zero-knowledge means the vendor holds nothing that could recover the data. The recovery secret (FR-SEC-4) is the only recovery path and it is held solely by the user. |
| OOS-P-4 | **Real-time collaborative editing / operational transform / CRDT document merging** | This is a file synchronizer. Whole-file conflict handling is the contract; sub-file semantic merging is a different product. |
| OOS-P-5 | **Content-aware three-way merge of user files** | The tool has no knowledge of file formats and will not attempt semantic reconciliation. Conflicts are preserved, not merged. |
| OOS-P-6 | **Acting as a backup product** with retention schedules, backup sets, or point-in-time full-system restore | Sync propagates changes, including destructive ones. Users must be told plainly that this is not a backup; see documentation Task 7.3.3. |
| OOS-P-7 | **Syncing anything other than regular files and directories** — device nodes, sockets, FIFOs, hard-link topology, extended attributes, alternate data streams, resource forks, sparse-file structure | No portable cross-platform representation exists. These are detected and reported, not silently dropped. |
| OOS-P-8 | **Provider-side deduplication or compression that depends on plaintext similarity** | Leaks content equality across users. |
| OOS-P-9 | **Telemetry, analytics, or crash reporting transmitted off the user's machine** | A privacy tool that phones home is not one. All diagnostics remain local. |
| OOS-P-10 | **Inventing cryptographic primitives** | Only well-reviewed, standard, published constructions. Selection is Story 2.2's work. |

### 4.2 Out of Scope for v1.0 (Revisit Post-GA)

| ID | Excluded from v1.0 | Rationale / Precondition to revisit |
| :--- | :--- | :--- |
| OOS-V-1 | **Multi-user shared access to one encrypted remote set** | Requires per-user key wrapping, revocation, and an access-control model. Precondition: a threat model extension covering revocation and member removal. |
| OOS-V-2 | **More than one sync pair per configuration** | Single-pair keeps the state model, locking, and CLI tractable for GA. Precondition: stable single-pair engine. |
| OOS-V-3 | **Graphical interface of any kind** | CLI-first per Key Assumption 2. |
| OOS-V-4 | **Storage backends other than Google Drive** | The abstraction boundary (FR-NET-6) is built in v1.0; the second implementation is not. |
| OOS-V-5 | **Google Shared Drives / Team Drives** | Different quota, permission, and ownership semantics. Personal Drive only for GA. |
| OOS-V-6 | **Block-level delta transfer** | A modified file is re-uploaded whole in v1.0. This is a known efficiency limitation and must be documented, not hidden. |
| OOS-V-7 | **Bandwidth throttling and transfer scheduling** | v1.0 bounds concurrency (NFR-NET-1) but does not rate-limit bytes. |
| OOS-V-8 | **Sync over LAN / peer-to-peer between devices** | All propagation is via the cloud backend in v1.0. |
| OOS-V-9 | **File-history browsing and restore beyond the soft-delete window** | Soft-delete (FR-DEL-5) is the only v1.0 restore mechanism. |
| OOS-V-10 | **Automatic self-update** | Updates come from the platform package manager or manual download. |
| OOS-V-11 | **Syncing to a path under another sync tool's managed directory** (nested/overlapping sync roots) | Detected and refused at init where reasonably detectable; not supported. |
| OOS-V-12 | **Case-insensitive-to-case-sensitive migration tooling** | Collisions are detected and reported (FR-PLT-3); automated remediation is deferred. |

### 4.3 Environmental Assumptions (Not Defended Against)

The product does not attempt to protect against these. They belong in the Story 1.2 threat model as accepted risk and in user documentation as stated limitations.

| ID | Assumption |
| :--- | :--- |
| OOS-E-1 | The local machine is trusted and not compromised. Malware with the user's privileges, a keylogger, a memory scraper, or a hostile OS defeats the tool. |
| OOS-E-2 | Plaintext exists at rest in the user's synced directory. Local full-disk encryption is the user's responsibility. |
| OOS-E-3 | The Go toolchain, standard library, and vetted dependencies are trusted; supply-chain integrity is managed by dependency policy (Task 2.1.3) and CI scanning (Task 5.4.1), not by runtime defenses. |
| OOS-E-4 | Traffic analysis by a network observer or the provider — transfer timing, volume, and object counts — is only partially mitigated. The residual leakage is enumerated in Story 1.2, not eliminated. |
| OOS-E-5 | Provider availability, durability, and account standing are the provider's responsibility. Account suspension or provider-side data loss is not recoverable by this tool. |
| OOS-E-6 | Denial of service by the provider or network is out of the tool's control; the tool degrades gracefully but cannot guarantee progress. |

## 5. Task 1.1.3 — Hardware Resource Consumption Bounds

### 5.1 Purpose

These are budgets, not measurements. They are the acceptance thresholds the Epic 5 benchmark and soak suites assert against, and they are the constraint that Epic 2 architecture must design toward. A design that cannot meet these bounds must be rejected at M1, not discovered at M6.

### 5.2 Reference Workloads

All bounds are stated against these corpora. Every corpus is measured on the reference hardware in §5.3.

| Corpus | Files | Directories | Total size | Shape |
| :--- | :--- | :--- | :--- | :--- |
| **W-S** (Small) | 10,000 | 1,000 | 10 GB | Typical documents corpus; mixed sizes, median ~200 KB |
| **W-M** (Medium) | 100,000 | 10,000 | 100 GB | Primary target. Deep nesting (max depth 12); includes a source tree with many small files |
| **W-L** (Large) | 250,000 | 25,000 | 500 GB | Supported upper bound for v1.0 |
| **W-B** (Big-file) | 100 | 10 | 200 GB | Large-object stress; individual files 1–20 GB |
| **W-X** (Churn) | 50,000 | 5,000 | 50 GB | 5% of files modified per hour, sustained, for steady-state soak testing |

**Stated capacity limit for v1.0**: 250,000 files / 500 GB in a single sync directory (W-L). Beyond this the tool must still function, but performance is not warranted and the documentation must say so. The tool must warn — not fail — when a scan discovers a corpus exceeding the supported bound.

### 5.3 Reference Hardware

| Tier | Specification | Role |
| :--- | :--- | :--- |
| **H-REF** | 4 physical cores with AES hardware acceleration, 8 GB RAM, SATA SSD, 100 Mbit/s symmetric link | The baseline all numeric bounds below are stated against |
| **H-MIN** | 2 cores, 2 GB RAM, spinning disk or eMMC, 10 Mbit/s link | Must remain *functional* and must not OOM. Throughput targets do not apply; memory ceilings do |
| **H-CI** | Whatever the CI matrix runners provide | Correctness only; performance assertions run on H-REF-equivalent runners or are skipped with a recorded reason |

H-MIN represents low-end NAS, SBC, and small VPS deployments. Its practical implication: **memory ceilings are hard limits, not targets scaled to available RAM.**

### 5.4 Memory Bounds (`NFR-MEM`)

| ID | Priority | Bound |
| :--- | :--- | :--- |
| NFR-MEM-1 | M | Idle daemon (watching, no transfers, no scan) resident set: **≤ 80 MB** at W-M. |
| NFR-MEM-2 | M | Peak resident set during a full reconciliation scan: **≤ 300 MB** at W-M, **≤ 600 MB** at W-L. |
| NFR-MEM-3 | M | Peak resident set during sustained transfer at maximum configured concurrency: **≤ 400 MB** at W-M, and **≤ 400 MB** at W-B — i.e. independent of individual file size. |
| NFR-MEM-4 | M | Memory usage must be bounded by *configured concurrency and buffer sizes*, not by corpus size, individual file size, or transfer queue depth. No whole-file buffering: a 20 GB file is processed as a bounded stream. |
| NFR-MEM-5 | M | The full local index is never required to be resident. Reconciliation operates over bounded working sets. |
| NFR-MEM-6 | M | No unbounded in-memory queue anywhere in the pipeline. Every producer/consumer boundary has a fixed capacity and applies backpressure. |
| NFR-MEM-7 | M | Under a 72-hour W-X soak, resident set must not exhibit monotonic growth; end-of-soak RSS within **+10%** of the 1-hour post-warmup baseline. |
| NFR-MEM-8 | M | The tool must complete a full sync of W-M on H-MIN (2 GB RAM) without OOM, without swap thrashing, and without requiring configuration changes. |
| NFR-MEM-9 | S | Buffer and cache sizing is user-configurable, with documented defaults and documented minimum viable values. |

### 5.5 CPU Bounds (`NFR-CPU`)

| ID | Priority | Bound |
| :--- | :--- | :--- |
| NFR-CPU-1 | M | Idle daemon: **< 1%** of one core, averaged over 5 minutes with no filesystem activity. Sub-1% must be achieved by blocking on events, not by polling faster than necessary. |
| NFR-CPU-2 | M | Default worker concurrency consumes at most **50% of available cores** (minimum 1, maximum 4) so the tool remains a background citizen on a machine in active use. |
| NFR-CPU-3 | M | Worker concurrency is user-configurable, including a single-worker mode for constrained hosts. |
| NFR-CPU-4 | S | Encryption throughput ≥ **150 MB/s per core** on hardware with AES acceleration. If a chosen construction cannot meet this, the shortfall must be raised at M2, not at M6. |
| NFR-CPU-5 | S | Encryption throughput ≥ **30 MB/s per core** on hardware without AES acceleration. |
| NFR-CPU-6 | M | Crypto and hashing must not be the bottleneck on H-REF: the tool must saturate a 100 Mbit/s link with default concurrency. |
| NFR-CPU-7 | M | Full reconciliation scan of an unchanged W-M corpus (warm OS page cache, no transfers): **≤ 60 seconds**. |
| NFR-CPU-8 | M | Change-detection latency for a single settled local file modification, from filesystem event to transfer enqueue: **≤ 5 seconds** at W-M, excluding the configured debounce interval. |
| NFR-CPU-9 | M | No busy-wait loops, and no unbounded goroutine growth. Goroutine count must be a function of configured concurrency, not of queue depth or corpus size. |

### 5.6 Disk I/O & Storage Bounds (`NFR-DSK`)

| ID | Priority | Bound |
| :--- | :--- | :--- |
| NFR-DSK-1 | M | Local index and metadata overhead: **≤ 1 KB per synced file**, i.e. ≤ 250 MB at W-L. |
| NFR-DSK-2 | M | Transient staging/temporary space is bounded by configured concurrency × chunk size, and must never require free space proportional to the total corpus. |
| NFR-DSK-3 | M | Staging space for a single in-flight download must not exceed the size of the file being downloaded plus a bounded constant. |
| NFR-DSK-4 | M | The tool checks for sufficient free space before beginning a download and fails cleanly with an actionable message rather than filling the volume. |
| NFR-DSK-5 | M | Reserved headroom: the tool refuses to consume the final **1 GB or 2%** of the target volume, whichever is larger. |
| NFR-DSK-6 | M | Index writes during a scan are batched, not per-file. Index fsync frequency must not scale linearly with file count. |
| NFR-DSK-7 | M | Files are written to the user's directory atomically: a partially-written file is never visible at its final path. |
| NFR-DSK-8 | M | All temporary and staging artifacts are reclaimed on clean shutdown and on next startup after an unclean shutdown. Orphaned temporaries must not accumulate across crash cycles. |
| NFR-DSK-9 | S | Idle daemon disk I/O is effectively zero: no periodic writes absent actual change or a scheduled scan. |
| NFR-DSK-10 | S | Full scans avoid re-reading file content when index metadata is sufficient to establish that a file is unchanged. |

### 5.7 Network Bounds (`NFR-NET`)

| ID | Priority | Bound |
| :--- | :--- | :--- |
| NFR-NET-1 | M | Default concurrent transfer streams: **4**, user-configurable. The tool does not open unbounded parallel connections. |
| NFR-NET-2 | M | The tool must not saturate the link to the point of starving other applications at default settings on a 100 Mbit/s link. |
| NFR-NET-3 | M | Protocol and metadata overhead: **≤ 5%** of transferred payload bytes for W-M under normal (non-retry) operation. |
| NFR-NET-4 | M | Idle daemon network usage is limited to token refresh and remote-change polling at the configured interval. Polling frequency must be a bounded constant, not a function of corpus size. |
| NFR-NET-5 | M | Retry backoff is exponential with jitter and a configured ceiling. Total request volume during a provider outage must be bounded and must not grow with outage duration. |
| NFR-NET-6 | M | A transfer interrupted at any point resumes without retransmitting more than one chunk of already-transferred data. |
| NFR-NET-7 | S | Remote object count and request volume stay within Google Drive's documented per-user quotas at W-L under steady-state operation. Quota headroom must be measured, not assumed. |

### 5.8 Startup, Shutdown & Responsiveness Bounds (`NFR-RSP`)

| ID | Priority | Bound |
| :--- | :--- | :--- |
| NFR-RSP-1 | M | Cold start to watching-and-ready at W-M: **≤ 15 seconds**, excluding password entry and any initial full scan. |
| NFR-RSP-2 | M | `status` returns in **≤ 2 seconds** at W-L and must not require a scan. |
| NFR-RSP-3 | M | Graceful shutdown completes in **≤ 10 seconds**, leaving no partial files at final paths and no unrecoverable in-flight state. |
| NFR-RSP-4 | M | Ungraceful termination (SIGKILL, power loss) at any point leaves recoverable state: the next start either resumes or cleanly rolls back, with no data loss and no index corruption. |
| NFR-RSP-5 | S | Interactive progress output updates at least every 2 seconds during active transfer, so a running transfer never appears hung. |

### 5.9 Measurement & Enforcement

| Aspect | Approach |
| :--- | :--- |
| **Corpus generation** | W-S through W-X are produced by a deterministic, seeded generator committed to the repository, so results are reproducible across machines and over time. |
| **Instrumentation** | Resident set, CPU time, goroutine count, disk bytes, and network bytes sampled at fixed intervals throughout each benchmark run; peak and time-series both retained. |
| **CI enforcement** | Correctness benchmarks run per-PR on H-CI. Numeric bounds in §5.4–§5.8 are asserted on H-REF-equivalent runners on a scheduled basis and at every release-candidate gate. |
| **Regression policy** | A **>10%** regression against the previous release baseline on any tracked metric fails the build and requires either a fix or an explicitly recorded, signed-off baseline revision. |
| **Soak testing** | The 72-hour W-X soak (NFR-MEM-7) is a mandatory M6 gate, not a per-PR check. |
| **Bound revision** | Any bound in this section may be revised only through the M1/M6 review gates with recorded rationale. Silently relaxing a threshold to make a build pass is a process violation. |
| **Traceability** | Owned by Epic 5: NFR-CPU-4/5 and NFR-DSK-1 map to Task 5.1.2; NFR-MEM-7 and NFR-RSP-4 map to Tasks 5.5.1–5.5.2; NFR-DSK-4/5 map to Task 5.5.3. |

## 6. Acceptance Criteria for Story 1.1
